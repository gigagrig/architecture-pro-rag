# Задание 4. Telegram-бот и проверочное API

## Устройство

Telegram → `run_bot.py` → `POST /ask` → E5 → FAISS → промпт → LLM → проверка ID источников → ответ.

API загружает существующий индекс из задания 3 один раз при старте. Запрос кодируется моделью из `manifest.json` с префиксом `query:` и нормализацией. Из пяти ближайших фрагментов в промпт попадают фрагменты со score не ниже 0,70. Это начальный порог, а не вероятность правильного ответа; его нужно подбирать на проверочных вопросах.

В [промпте](rag_bot/prompts.py) есть два few-shot примера: ответ о сестре Kael Ardyn и отказ на вопрос о его любимом десерте. Положительный пример взят из `knowledge_base/entity_01.md`. Для требования Chain-of-Thought используется краткое объяснение по проверяемым фактам: найденный факт → связь с вопросом → вывод. Бот не выводит подробные внутренние рассуждения модели.

LLM возвращает JSON: ответ, обоснование, признак неизвестного ответа и цитаты. Приложение проверяет, что каждый указанный фрагмент участвовал в текущем поиске и текст цитаты не пуст. Если подтверждение отсутствует, возвращается «Я не знаю». Сравнение цитаты с текстом документа не выполняется. Такая проверка отсеивает неизвестные ID источников, но не проверяет точность цитаты или обоснованность ответа. Поэтому предусмотрены ручные и автоматические проверки качества.

Вопросы независимы; память диалога не используется. В учебной версии одновременно обрабатывается один запрос генерации, остальные обращения к API получают HTTP 429. Telegram-процесс обрабатывает сообщения последовательно. Он использует long polling, поэтому публичный сервер и webhook не нужны. При перезапуске возможно повторное получение последнего ещё не подтверждённого сообщения.

## Подготовка

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
cp -n .env.example .env
```

Если окружение уже подготовлено, достаточно активировать его и установить обновлённый `requirements.txt`. Токен хранится в существующем `telegram_bot_token.txt` одной строкой. Файл исключён из Git и Docker build context. Не вставляйте токен в команды или документацию.

## Подключение модели

Для Yandex Alice AI LLM Flash положите ключ в `yandex_ai_api_key.txt` (файл исключён из Git) и задайте в `.env`:

```dotenv
LLM_BASE_URL=https://ai.api.cloud.yandex.net/v1
LLM_MODEL=gpt://b1g2bu1h99h8aoj25qf5/aliceai-llm-flash/latest
LLM_API_KEY=
LLM_API_KEY_FILE=yandex_ai_api_key.txt
```

В Docker ключ монтируется только в API через secret. Эмбеддинги вычисляются локально, вопрос и найденные фрагменты отправляются в Yandex. Токен Telegram в запрос LLM не передаётся.

Клиент использует [Chat Completions API](https://aistudio.yandex.ru/ru/docs/ai-studio/api/Chat-Completions/createChatCompletion) со структурированным JSON по схеме `GeneratedAnswer`, температурой 0,3 и пределом ответа 1500 токенов. Повторного запроса для исправления цитат нет. Неизвестный chunk_id или пустая цитата приводят к «Я не знаю»; ошибки связи и формата возвращаются как HTTP 503.

Остальные настройки описаны в [.env.example](.env.example). `TELEGRAM_ALLOWED_USER_IDS` позволяет ограничить доступ числовыми Telegram ID через запятую; пустое значение разрешает все личные чаты. API предназначено для локальной проверки, без авторизации.

## Запуск без Docker

Первый терминал, из корня проекта:

```bash
source .venv/bin/activate
python -m uvicorn rag_bot.api:app --host 127.0.0.1 --port 8000
```

Дождитесь `Application startup complete`. Если кеш эмбеддингов отсутствует, установите `LOCAL_FILES_ONLY=false`: первая загрузка займёт около 1,1 ГБ. Затем можно вернуть `true`. Используйте один процесс API: каждый дополнительный worker загружает отдельную копию модели.

Второй терминал:

```bash
source .venv/bin/activate
python run_bot.py --check
python run_bot.py
```

`--check` только проверяет токен, выводит ссылку на бота и наличие webhook; сообщения не получает и не отправляет. Если webhook уже настроен, приложение завершится с пояснением, сохранив текущую настройку. Для работы polling должен быть запущен только один экземпляр бота. `Ctrl+C` останавливает соответствующий процесс.

Проверка человеком: [TELEGRAM_TESTING.md](TELEGRAM_TESTING.md).

## Проверка API

Откройте [Swagger UI](http://127.0.0.1:8000/docs), выберите `POST /ask` → Try it out и отправьте:

```json
{"question": "Кто отец Kael Ardyn?"}
```

Или выполните:

```bash
curl -fsS http://127.0.0.1:8000/health
curl -fsS http://127.0.0.1:8000/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Кто отец Kael Ardyn?"}'
python check_api.py --output task4_api_results.json
```

`GET /health` показывает загрузку индекса, число фрагментов и выбранную LLM; доступность генерации он не проверяет (`llm_status: not_checked`). `POST /ask` возвращает `answer`, `explanation`, `unknown`, `sources`, `retrieved_count`, `model` и исходный `question`. У источника есть путь, название, score, ID фрагмента и цитата, возвращённая моделью.

Коды ошибок: 422 — пустой/слишком длинный вопрос; 429 — генерация занята; 503 — ошибка доступа к LLM, таймаут или некорректный формат её ответа. Отсутствие фактов — успешный ответ HTTP 200 с `unknown=true`, а не техническая ошибка.

Скрипт `check_api.py` задаёт пять вопросов с известными ответами и два без ответа, проверяет ключевые факты, наличие источников и сохраняет реальные ответы и время запросов в JSON. Это базовая проверка, не полноценная оценка качества. Вопросы и ожидаемые факты приведены в инструкции Telegram.

Реальные примеры: [пять ответов и два отказа](task4_dialogues.md), [полный JSON-отчёт](task4_api_results.json).

Автоматические тесты без внешних сервисов:

```bash
python -m unittest discover -s tests -v
```

Они проверяют связку обработчика Telegram с реальным маршрутом API, подменяя только транспорт Telegram, поиск и LLM. Отдельно проверяются контракт HTTP-клиента, источники, отказ, ошибки и валидация. Эти тесты не заменяют генерацию реальной моделью.

## Docker

FAISS — встроенная библиотека, а не отдельный сетевой сервер. Compose запускает два сервиса: API с индексом FAISS и Telegram-процесс. После подготовки `.env`, файлов ключей и индекса:

```bash
docker compose up -d --build
docker compose logs -f api bot
docker compose down
```

Индекс монтируется только для чтения, кеш E5 сохраняется в `.cache/embeddings`. Ключ Yandex монтируется только в API, токен Telegram — только в бот, оба через secrets. API опубликовано на `127.0.0.1:8000`. Не запускайте одновременно контейнер бота и `python run_bot.py`.

Адрес и URI модели берутся из `.env`. В Compose переопределяется только путь к ключу: `/run/secrets/yandex_api_key`. Для остановки сервисов используйте `docker compose down`.

## Использованные интерфейсы

- [Telegram Bot API](https://core.telegram.org/bots/api): `getMe`, `getWebhookInfo`, `getUpdates`, `sendMessage`, `sendChatAction`.
- [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/): загрузка ресурсов при старте приложения.
- [Yandex AI Studio Chat Completions](https://aistudio.yandex.ru/ru/docs/ai-studio/api/Chat-Completions/createChatCompletion): генерация и структурированный JSON.

Ограничения: нет истории диалога, потоковой выдачи, распределённой очереди и полной защиты от prompt injection. Расширенная демонстрация защиты относится к заданию 5.
