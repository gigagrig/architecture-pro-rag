# Исследование моделей и инфраструктуры

Дата проверки информации и цен: **14 сентября 2026 года**.

## 1. Исходные условия

У компании около 21 000 документов, и база растёт примерно на 400 страниц в месяц. В документах могут быть исходный код, архитектурные решения и внутренние правила. Поэтому важны не только качество ответов, но и защита данных.

Для сравнения я использовал следующие примеры:

- локальная LLM — `Qwen/Qwen2.5-14B-Instruct`;
- облачные LLM — OpenAI GPT-5.6 Luna / Terra и YandexGPT Pro 5.1;
- локальная модель эмбеддингов — `intfloat/multilingual-e5-base`;
- облачная модель эмбеддингов — OpenAI `text-embedding-3-small`.

## 2. Сравнение LLM

| Критерий | Локальная Qwen2.5 14B | OpenAI GPT-5.6 | YandexGPT Pro 5.1 |
|---|---|---|---|
| Качество | Подходит для RAG и поддерживает русский язык. Результат нужно проверять на вопросах компании | Luna рассчитана на экономичные массовые запросы, Terra — на более сложные задачи. Точный результат нужно измерить | Русский язык является приоритетным. Для английских и финских документов нужна отдельная проверка |
| Скорость | На GPU работает приемлемо, на CPU будет медленно. Скорость полностью контролирует компания | Быстрый старт без своего GPU. Есть задержка сети и ограничения API | Быстрый старт без своего GPU. Также зависит от сети и доступности сервиса |
| Стоимость | Нет оплаты за токены, но нужны GPU, электричество и сопровождение | Оплата за токены. Luna: $0,20 за 1 млн входящих и $1,20 за 1 млн исходящих токенов; Terra: $2 и $12 соответственно | Pro 5.1: 0,8 ₽ за 1000 входящих и 0,8 ₽ за 1000 исходящих токенов |
| Развёртывание | Самый сложный вариант: нужны vLLM или другой сервер, мониторинг и обновления | Самый простой вариант: достаточно API и секретного ключа | Простой вариант через API Yandex AI Studio |
| Конфиденциальность | Документы остаются внутри инфраструктуры компании | Найденные чанки отправляются внешнему провайдеру | Найденные чанки отправляются в Yandex Cloud |

Qwen2.5-14B имеет 14,7 млрд параметров, поддерживает более 29 языков и контекст до 128 тысяч токенов. Это делает её подходящей локальной моделью для первого прототипа. Однако перед продакшном качество нужно проверить на собственных вопросах компании.

OpenAI указывает, что данные API по умолчанию не используются для обучения моделей без согласия клиента. При этом журналы контроля злоупотреблений могут храниться до 30 дней. Для европейского региона доступны специальные настройки хранения и обработки данных, но они требуют согласования и дополнительных условий. Поэтому секретные документы нельзя отправлять в облако автоматически.

### Вывод по LLM

- Для обычных внутренних документов удобнее начать с **GPT-5.6 Luna**.
- Для сложных вопросов можно повторять запрос через **GPT-5.6 Terra**.
- Для документов с высоким уровнем секретности нужна **локальная Qwen2.5-14B**.
- YandexGPT имеет смысл выбрать, если основная часть документов и запросов будет на русском языке.

## 3. Сравнение моделей эмбеддингов

| Критерий | Локальная `multilingual-e5-base` | OpenAI `text-embedding-3-small` |
|---|---|---|
| Создание индекса | На CPU медленнее, чем через мощный облачный сервис, но нет сетевых запросов и лимитов API | Удобна для пакетной обработки, но скорость зависит от сети и лимитов API |
| Качество поиска | Поддерживает много языков и создана для семантического поиска. Нужно добавлять префиксы `query:` и `passage:` | Сильная универсальная облачная модель. Итоговое качество всё равно нужно проверять на golden set компании |
| Размер вектора | 768 чисел | Размер можно настраивать через параметр `dimensions` |
| Ограничения | Текст длиннее 512 токенов обрезается | Один вход ограничен 8192 токенами |
| Стоимость | Нет платы за запросы. Используются CPU/RAM компании | $0,02 за 1 млн токенов |
| Конфиденциальность | Полный текст остаётся внутри компании | Полный текст отправляется во внешний API при индексации |

### Вывод по эмбеддингам

Я выбираю **`intfloat/multilingual-e5-base`**. Она работает локально, поддерживает много языков и создаёт векторы размером 768. Для базы QuantumForge это важнее небольшой экономии времени при облачной индексации.

Перед окончательным выбором нужно сравнить локальную и облачную модели на 30–50 реальных вопросах. Главная метрика — доля случаев, когда правильный документ попал в первые 5 результатов (`Recall@5`).

## 4. Сравнение FAISS и ChromaDB

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Поиск | Очень быстрый поиск непосредственно в памяти процесса. `IndexFlat` даёт точный результат | Быстрый векторный поиск через коллекции. Есть дополнительный слой хранения и API |
| Индексация | Простое добавление готовых векторов. Метаданные нужно хранить отдельно | Хранит документы, векторы и метаданные вместе |
| Внедрение | Минимум компонентов для одного Python-приложения | Немного сложнее, но можно запустить локально, в Docker или как отдельный сервер |
| Удобство | Хорош для небольшого прототипа. Нет полноценного API, пользователей и фильтров документов | Есть фильтрация по метаданным и тексту, persistent client и клиент-серверный режим |
| Поддержка | Нужно самостоятельно сохранять индекс, метаданные и делать резервные копии | Больше возможностей из коробки, но появляется отдельный сервис для сопровождения |
| Стоимость | Бесплатная библиотека; оплачиваются только ресурсы сервера | Open-source-вариант бесплатен; оплачиваются сервер, диск и сопровождение |

FAISS хранит индекс в RAM. Для оценки возьмём 200 000 чанков и векторы размером 768 в формате `float32`:

```text
200 000 × 768 × 4 байта ≈ 586 МиБ
```

Даже с метаданными этот объём небольшой для сервера с 32 ГБ RAM.

### Вывод по векторной базе

Для проектной работы я выбираю **FAISS (`IndexFlatIP`)** по следующим причинам:

- база пока небольшая;
- поиск будет точным;
- библиотека запускается внутри Python-приложения;
- не нужен отдельный сервер базы данных;
- нет лицензионной оплаты.

Перед добавлением векторы нужно нормализовать, тогда inner product можно использовать как cosine similarity. Метаданные и права доступа будут храниться отдельно. Если появятся несколько команд, сложные фильтры или несколько экземпляров бота, стоит перейти на ChromaDB либо другую серверную векторную базу.

## 5. Варианты решения

| Вариант | Состав | Плюсы | Минусы |
|---|---|---|---|
| 1. Полностью локальный | Qwen2.5-14B + multilingual-e5-base + FAISS | Данные не покидают компанию, нет цены за токены | Нужен GPU, сложнее поддерживать, качество надо тщательно проверять |
| 2. Полностью облачный OpenAI | GPT-5.6 Luna + text-embedding-3-small + ChromaDB | Самый быстрый запуск и простая разработка | Тексты передаются провайдеру, есть плата за API и зависимость от него |
| 3. Гибридный | OpenAI для обычных данных, локальная Qwen для секретных, локальные embeddings + FAISS | Баланс качества, цены и конфиденциальности | Нужна классификация документов и маршрутизация запросов |
| 4. Yandex Cloud | YandexGPT Pro + облачные embeddings + ChromaDB | Удобно для русскоязычных запросов, простой API | Не лучший основной вариант для финско-эстонской компании; данные уходят в другой облачный сервис |

### Выбранный вариант

Лучшим считаю **вариант 3 — гибридный**.

Индекс и исходные документы остаются внутри инфраструктуры QuantumForge. Обычные запросы можно отправлять в OpenAI, а секретные — только в локальную модель. Это дороже и сложнее полностью облачного варианта, но лучше соответствует требованиям безопасности и SOC 2.

Для учебной версии можно сначала реализовать упрощённую часть этого решения: `multilingual-e5-base` + FAISS + одна доступная LLM. После этого добавить классификацию документов и локальный маршрут.

## 6. Рекомендуемая конфигурация сервера

### Сервер бота и индекса

- CPU: **8 vCPU**;
- RAM: **32 ГБ**;
- диск: **100 ГБ SSD/NVMe**;
- GPU: **не требуется** для FAISS и ежедневной пакетной индексации;
- размещение: отдельный deployment в существующем AWS EKS;
- резервная копия: индекс, метаданные и исходные документы в закрытом S3-бакете.

Этой конфигурации достаточно для пилота с облачной LLM. Точную нагрузку нужно проверить тестом с ожидаемым числом одновременных пользователей.

### Дополнительный сервер для локальной LLM

- CPU: **16 vCPU**;
- RAM: **64 ГБ**;
- GPU: **NVIDIA L4 24 ГБ** или аналог;
- диск: **200 ГБ NVMe**.

Qwen2.5-14B занимает около 30 ГБ в BF16, поэтому на GPU с 24 ГБ модель нужно запускать в 4-битной или 8-битной квантизации. Для полной BF16-версии потребуется GPU с большим объёмом памяти.

## 7. Итог

Мой выбор для проектной работы:

- **векторная база:** FAISS `IndexFlatIP`;
- **эмбеддинги:** `intfloat/multilingual-e5-base`, 768 измерений;
- **LLM:** облачная модель для разрешённых данных и локальная Qwen2.5-14B для секретных;
- **основной сервер:** 8 vCPU, 32 ГБ RAM, 100 ГБ SSD, без GPU;
- **локальная LLM:** отдельный GPU-сервер при необходимости.

Такой подход достаточно простой для первого прототипа, не требует отдельной векторной СУБД и оставляет возможность дальнейшего роста.
